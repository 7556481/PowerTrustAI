## 本轮实现

原`OfflineHarness.run/cancel`签名与结果契约保留。[runtime.py](../harness/runtime.py)持有原组件、运行任务注册表和取消入口，每次调用创建一个[RunExecution](../harness/execution.py)运行上下文；原嵌套变量成为该运行独有字段，预算、deadline、证据和历史轮次不在不同运行间共享。

`RunExecution`是原Harness运行体的阶段抽取，不是第二个任务调度服务；原服务队列、组件工厂、observer、Retriever与政策未变。每次只运行原顺序驱动一次，不存在图失败后再走旧路径重发。异常从`harness.runtime`继续导出，原导入位置保持可用。

|共享阶段|作用与保留边界|
|---|---|
|`validate_saved_inputs`|合法状态进入与原索引证据校验；请求与模式等前置校验仍早于Agent|
|`generate`|原检索、条件查询转换、生成与仅生成/无实质回答终态|
|`extract_and_tools`|按当前回答版本提取，运行原有限单位换算检查，保留预算与原始输出|
|`prepare_review`|按purpose顺序检索，构建两侧独立证据输入、原引用及有效生成快照|
|`review_pair`|保留双审原并发、同伴部分结果及取消清理；仅证据模式不执行领域审核|
|`merge_and_decide`|原条件主体补检、证据冲突处理、政策及执行/覆盖/检索门禁；返回是否已终止|
|`revise`|原修订校验和版本推进；成功后回到提取及完整双审，失败保留上一轮信息|

调用、计费记录归属、trace/observer、合法状态转换与最终结果组装仍在同一运行上下文中。未复制政策、解析或纠正实现，未改Agent提示、schema、模型和检索设置。本轮没有节点图；未来适配必须让图真正控制这些阶段与条件分支，不能把`RunExecution.run()`整个包装成一个节点冒称完成迁移。

## 初次检查失败与修正留痕

1. 差分初始化首次失败、0项执行：误将已有清单的工作区CRLF哈希用于Git/LF字节。核实仅换行不同后分别绑定两个固定哈希，没有放宽原文件身份要求。
2. 第二次差分10项通过、1项失败：旧/新输出比较已一致，新增断言误把完成顺序记录要求为调用编号排序。原实现实际为`[3,2,4]`，因此仅改测试的编号集合检查；运行记录仍按原完成顺序完整比较，没有排序或修改真实日志。
3. 测试夹具直接借用异步TestCase的清理入口，未启动其独立runner，出现临时目录ResourceWarning；改为显式关闭该合成Retriever和临时目录。最终启用资源警告即错误的差分通过。不是模型或生产失败。

没有发现尚未解释的运行行为差异。只读核对保留原基线报告/预期/匹配/冻结/完整预测文件，历史attempt不删、不恢复；7份原公开文件及35份执行冻结绑定文件哈希未改变。本轮真实模型请求和费用均为0。

## Agent和工具如何定制

可以分别定制Agent职责、输入/输出契约、模型配置和工具权限，以及流程中的顺序、分支和循环。LangGraph提供图执行机制，语义规则与授权仍由项目实现；节点可以直接调用现有Python方法，无需把每个Agent重新写成通用聊天Agent。[官方Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

工具可由项目自行编写，或按需接入第三方库/API/MCP工具；只引入实际需要的依赖。可定义工具名称、说明、参数和输出，再决定由程序固定调用还是允许模型选择；“安装依赖”“接通服务”“允许某个Agent使用”是三个独立决定。[官方工具文档](https://docs.langchain.com/oss/python/langchain/tools)

本项目已有[ToolSpec/ToolRequest/ToolResult](../tools/contracts.py)及[单位换算工具](../tools/unit_conversion.py)，后者校验调用角色，检查输入并返回带版本的结果；Retriever另按现有知识快照与证据协议交付。这些可以复用。后续若增加工具，按Agent分配允许范围、超时/用量和读写权限，工具结果照样接受证据/业务校验；安装更多工具不等于判断更可靠。本轮没有新工具、依赖安装或工具选择协议变更。

下一阶段若获授权，才锁定图依赖并添加真实阶段路由的可选图路径，继续先离线验证。旧组件付费授权不延续；生产、v7提示/v6解析和原参考标签均保持既有身份。
