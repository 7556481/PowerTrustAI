# 1. 项目目标、适用范围与学习路线

## 1.1 要解决的具体问题

电力问答中的一句话可能同时包含技术事实、数值换算、适用条件、资料引用和工程建议。自然语言流畅并不代表这些部分都成立。PowerTrustAI 将回答冻结后拆成可审核主张，分别检查证据支持与领域边界，把程序能够确定的规则和工具结果单独保存，最后交给确定性政策决定结束或有限修订。

两个入口复用同一套运行流程：问答模式先生成回答，已有回答模式直接审核用户提供的文本。后者不是重新生成一篇答案再假装在审核原文。两种模式都需要保存实际 answer_id、版本及提取结果，保证后续发现指向确切文本。

本机原型适用于学习、概念资料核查和人工辅助复核。已有公开资料的适用地域、发布时间和文件质量影响可用范围。项目没有执行潮流、短路、稳定性或厂站仿真，没有多用户权限系统，也没有公网部署。不存在一个已经验证的“可信总分”。

## 1.2 四种不同的成功

| 层次 | 能够说明什么 | 不能说明什么 |
|---|---|---|
| 程序测试通过 | 受测输入下的接口、校验和状态符合断言 | 未受测场景中的模型理解正确 |
| 执行阶段完成 | 必需调用返回并形成合法阶段对象 | 每项工程检查都可评估 |
| 主张 supported | 当前模型判断与绑定依据支持这一主张 | 全回答安全、资料适用或模型没有漏检 |
| 工程安全认证 | 需要专业流程、工程输入与责任体系 | 本项目没有提供此能力 |

例如运行已经 finished，双审阶段也完整，但领域审核因缺少工况或工程输入报告 not_assessable，这些状态可以同时成立。反过来，即使若干主张 supported，另一条审核响应结构失败，执行完整性也不能被这些成功条目覆盖。

## 1.3 推荐学习路线

先读 `backend/assembly.py`，看最终组件如何装配；再读 `harness/runtime.py` 和 `harness/policy.py`，理解控制权；随后读 `core/models.py`，认识回答、主张、发现与依据。接下来沿两个分支阅读：一条进入 `rag/` 学习原文与检索，另一条进入 `agents/` 和 `services/` 学习模型契约及程序校验。

最后阅读应用层的 `backend/service.py`、`backend/store.py` 与 `backend/static/app.js`，把“一个模型调用”放回真实用户操作中。不要先背每个提示词版本；应先知道哪个版本由真实服务显式采用，哪些只是历史兼容代码。

学习目标是能够回答三件事：某条结论究竟来自模型、程序还是人工？它绑定哪个回答版本、哪段证据？失败后服务究竟保存了什么？这比记住测试总数更接近项目的工程价值。

本章依据：`docs/prototype-v0.1.md`、`docs/design-decisions.md`、`backend/assembly.py`、`core/models.py`。当前原型的实际验证分层见第 11、13 章；历史方案的迁移边界见第 15 章。

# 2. 最终架构与一次请求的生命周期

## 2.1 模块依赖方向

界面只调用同源 API，不读取 SQLite 或运行文件。API 将经过校验的输入交给 ApplicationService；服务管理运行身份、排队、取消及持久化，并通过 ComponentFactory 装配原有 OfflineHarness。Harness 调用 Agent、ClaimExtractor、Retriever 和工具；底层适配器负责模型协议与调用记录。

<!-- diagram:architecture -->

这里的 OfflineHarness 名称来自项目的离线工程基础，不表示真实服务仍使用假模型。真实装配向它注入真实适配器、BM25 检索与当前审核组件；演示装配注入 synthetic_fixture 假组件。核心流程和确定性政策没有被前端重新实现。

| 层 | 主要职责 | 应避免承担的职责 |
|---|---|---|
| Web 页面 | 收集输入、显示状态与版本、追加意见 | 决定审核政策、拼接数据库路径 |
| API | 鉴权、输入验证、作用域及错误响应 | 自动调整预算、接受任意文件路径 |
| 应用服务 | 排队、状态管理、运行存储、生命周期 | 创建另一套模型审核逻辑 |
| Harness | 阶段顺序、预算、双审、修订、部分结果 | 让模型自行决定无限重试 |
| Agent 与服务 | 生成、提取、审核、修订及契约检查 | 越过冻结版本或偷换依据 |
| Retriever / Tool / Adapter | 原文检索、有限计算、模型请求 | 将检索相似度当作事实支持 |

## 2.2 从 POST 到可恢复结果

用户提交后，服务验证 mode 与字段，生成 run_id 并保存运行。若已有活动任务则进入等待队列；当前基线允许一个活动运行、两个等待位置。提交响应立即返回身份，浏览器开始 GET 状态，不能因为超时再自动 POST 一遍。

运行开始时记录实际装配与预算。问答模式生成初稿后冻结；已有回答模式直接建立初稿。随后提取主张、独立双审、程序检查、政策决定；可能进入一次 Revision，再完整重提取和双重审。每次有效检查点保存版本、阶段产物和事件，未完成时也可以查询已经有效的部分。

<!-- diagram:flow -->

运行对象跨越请求生命周期：POST 返回后后台仍执行，页面可以刷新；Model Adapter、Retriever 的资源则属于服务装配，必须在停止时排空或关闭。SQLite 记录跨越进程重启，页面内存中的令牌不跨越刷新。理解这些不同寿命，才能解释为什么页面关闭不等于任务取消。

## 2.3 为什么不另建前端构建系统

本机演示需要的是明确身份、可查看证据和可追加复核，不需要复杂客户端状态框架。现有 backend 同源提供 HTML/CSS/JavaScript，减少双端端口、CORS、构建链和配置漂移。代价是页面逻辑需要自己处理并发响应、错误状态和安全文本渲染；项目通过显式请求锁及视图代次控制这些问题。

这是一项原型规模的取舍，不是宣称所有项目都不应使用前端框架。若未来出现多页面权限、复杂编辑、规模化组件复用，必须重新评估；当前任务没有引入这些范围。

阅读入口：`backend/api.py`、`backend/service.py`、`backend/assembly.py`、`harness/runtime.py`、`backend/static/app.js`。先从一次提交追踪调用，再回头读辅助类型，能避免在所有历史 Agent 模块之间迷失。

## 2.4 图中三类关系

实线箭头表示控制调用：页面→API→应用服务→Harness，以及Harness调用审核组件。蓝色虚线表示数据访问：Retriever读取固定知识库，应用服务读取/更新运行SQLite。橙色点线表示观察回调：Harness将检查点snapshot交给应用服务注册的observer，再由RunStore写事务。

# 3. 四 Agent、主张提取与 Harness

## 3.1 “Agent”在本项目中的含义

四 Agent 是职责分离的受控组件：Generation 生成证据约束的初稿；EvidenceVerification 判断事实与依据；PowerDomainReview 检查领域适用条件和缺失前提；Revision 根据已观察发现作有限修改。它们没有自由创建无限任务，也没有权力越过预算或批准自身结果。

ClaimExtractor 是单独服务，不应为了凑“四 Agent”把它隐藏或合并到事实审核中。它将冻结回答映射成原子主张、回答区间和审核义务，影响下游到底审核什么。提取错误会传播到两个审核分支，所以它并不是无风险的预处理。

Harness 是控制器，不是第五个自由判断模型。它决定何时调用组件、如何记录阶段、何时停止；业务结论由确定性政策根据结构化发现计算。模型可以提出理由，但不能单凭“看起来已完成”跳过必需阶段。

## 3.2 当前真实装配的版本表

| 组件 | 当前服务显式采用 | 重要边界 |
|---|---|---|
| Generation | evidence-bound-generation-v3-answer-units | 程序定位实际回答单元 |
| ClaimExtractor | atomic-claims-v7-obligations | 目标、角色及义务仍可能有语义错误 |
| 事实审核 | schema12 / evidence-verification-v9.4-standalone-templates | 独立模板，类型依据与版本校验 |
| 领域审核 | power-domain-review-v3.1-applicability | 缺工程前提时不能虚构评估 |
| Revision | bounded-revision-v2-per-finding-actions | 每个冻结 finding 均需交代动作 |
| 确定性政策 | limited-repair-policy-v1 | 最多一次修订，仍需人工复核 |
| 演示领域规则 | power-demo-rules-v1.1 | 不是经过生产审定的电力规程 |

代码中保留旧版契约用于历史解释和测试，不意味着当前 API 使用旧版。个别 finding 的复用 checker 标签也不应替代运行 manifest 和实际请求模板；确认版本必须从装配、输出 prompt_version 和冻结归档交叉核对。

## 3.3 冻结回答与共享主张

冻结意味着某轮审核的 answer_id、answer_version、全文及区间不再随模型临时修改。两个审核分支接受同一份提取结果，减少“一个分支在审甲回答，另一个在审乙回答”的漂移。Revision 产生新版本，不原地改写 v1；新版本必须重新提取，旧主张不能被直接复用为 v2 的审核结论。

共享主张让目标一致，却也形成共同上游风险：若提取器把技术断言错分为回答范围声明，两个分支都可能收到错误任务。双审的职责独立并不等于统计独立；当前使用同一提供方模型，还共享提取结果，不能宣称已通过多模型投票消除了相关错误。

## 3.4 如何读模型契约

先看输入：冻结回答、claims、quote candidates、工具结果及允许类型；再看输出：每个 finding 需要什么身份、状态与 bases；最后看校验器如何拒绝未知 ID、错版本及不属于该 claim 的依据。提示词只是告诉模型该做什么，程序校验器才决定返回数据能否进入当前运行。

一个合法 JSON 也可能是错误判断。程序能验证区间、类型和身份，通常不能直接证明模型正确理解了句子的语义。面试时应主动用第 12 章的目标分类漏检说明这个边界，而不是把 schema12 当成“已经解决幻觉”。

阅读入口：`agents/contracts.py`、`services/claim_extractor.py`、`agents/review_templates_v3.py`、`agents/verification_contract_v9_scoped.py`、`services/review_fidelity.py`。

# 4. 知识入库、原文与 PDF 质量边界

## 4.1 原文和检索文本为什么分开

检索需要去噪、分词或规范化，引用却需要精确回到原文。项目保存 raw text，并另外派生 search_text。只修改搜索表示，不把规范化后的空格、单位或标点写回 Evidence。否则一个看似方便的预处理可能让 quote offsets 无法回查，甚至让“引用原文”变成程序重写的文本。

Markdown 与 PDF 的来源对象、片段及派生版本都通过存储层建立关联。原文件哈希、解析器信息和切分版本属于可复现性线索；它们能说明某个片段来自哪次解析，不能说明解析内容已经被人工逐页视觉核对。

## 4.2 PDF 文本不是视觉原文

PDF 可能有多栏、跨页表格、上下标、公式和页眉。解析出的字符顺序不一定等于视觉阅读顺序。当前资料回查展示的是提取文本，并保留质量告警，如视觉未核对、公式或表格未解释。界面不能把它称为“已核验的 PDF 原文”。

`pdf-paragraphs-v2` 优先使用可靠空行段落边界，长段按有界窗口切分，最大约 1200 字符；不在 CRLF 中间切断。派生片段基于已保存的页文本生成，不为每个实验重新解析官方文件。这样可以把切分变化与解析变化分开追踪。

| 资料处理层 | 保存的对象 | 需要保留的疑问 |
|---|---|---|
| 文件接入 | 文件来源、哈希、文档身份 | 版权、地域、版本与获取是否成功 |
| 文本解析 | 页文本、解析器版本 | 视觉顺序、公式和表格是否可靠 |
| 片段派生 | 原文区间、页码、切分版本 | 边界是否切开必要条件 |
| 搜索表示 | search_text、索引配置 | 去噪是否改变召回，不改变原文 |
| Evidence 展示 | 文本与原文定位、质量告警 | 支持关系仍须模型及人工评估 |

## 4.3 当前公开资料和获取失败

资料说明登记了三份实际获取的公开来源：NERC Reactive 指南、VAR 标准资料及 PNNL 报告。PDF 质量派生记录分别为 57 页/268 片段、16 页/40 片段、54 页/116 片段，合计 127 页、424 派生片段。这是入库规模，不是 424 个正确答案或全部已视觉核验的证据。

AEMO 获取曾返回 403，没有因此虚构已入库内容，也没有自动绕过访问限制。官方全文留在本机忽略的 data 目录；公开可访问不自动等于允许项目重新分发全文。Git 中保存来源 manifest、说明及开发问题，不提交整份 PDF。

## 4.4 相邻上下文

检索命中片段可能需要前后条件，因此 Harness 的当前装配启用有界相邻上下文。上下文来自相同文档版本的机械邻接，保持各片段自己的 Evidence 身份，不给邻居伪造核心命中的排名或相似度。超出预算时省略整个片段，不切成无法定位的新引文。

相邻不保证语义连续，跨页也不保证同一表格。曾有 cross_page_next_first 交付实验，未被自动推广为默认配置。特别注意：某些 CLI 文档中“默认关闭上下文”的描述指该命令入口，当前真实 Harness 的 ContextOptions 装配应看 `backend/assembly.py`，不能仅凭历史文档推断。

阅读依据：`rag/markdown.py`、`rag/pdf.py`、`rag/pdf_chunks.py`、`rag/storage.py`、`rag/context.py`、`docs/pdf-retrieval-quality.md`、`docs/knowledge-sources/manifest.json`。

# 5. BM25、Dense、RRF 与检索取舍

## 5.1 当前默认为什么仍是 BM25

BM25 用词项出现、文档长度和集合频率计算相关性。当前实现对拉丁文本提取小写词项，对中文使用单字和双字组合；查询词去重，只保留分值大于零的片段，先按BM25分数降序主排序，平分才使用稳定身份。平分键依次为 document_id、version、ordinal、fragment_id，按字段本身的升序比较，不依赖SQL返回顺序或插入时间；version的升序不是“优先最新版本”，候选已受固定快照限制。参数 k1=1.5、b=0.75，使用正值 IDF。默认服务使用 AsyncSQLiteBM25Retriever，核心结果数量为 3，再装配有界上下文。

它的优点是容易追踪、资源要求低、无需模型编码服务；局限是同义表达、跨语言和自然问题不一定命中术语。BM25 分数解释的是查询与搜索表示的词项关系，并不是文件权威性或回答正确概率。

## 5.2 Dense 编码的实际实现

可选 Dense 路径采用固定 revision 的 multilingual-e5-small，384 维、FP32 ONNX CPU，分别编码 query 与 passage。attention mask 均值池化后 L2 归一化；长文档以 480 token 窗口、448 stride 分段，各窗口先做mask均值池化；窗口池化向量等权平均后才做一次L2归一化，并非先逐窗口L2后再平均。最大批量为 4。具体 revision 与文件哈希见 `rag/embedding.py`，不是运行时随意下载最新版。

向量只是一种搜索派生物，不替代 raw text。索引建立时记录 encoder profile、知识版本和来源指纹；维数、有限值与快照完整性都需检查。若向量缺失，不能悄悄把不完整 Dense 排名说成同一完整实验。索引构建采用原子更新，失败回滚，不污染已有知识表示。

## 5.3 RRF 的意义与边界

RRF 按名次融合，不要求 BM25 与余弦分值在同一尺度。当前可选实现使用 k=60、两路等权、候选深度 50，Dense 仅使用正相关候选。直观上，片段在两种方法都靠前会得到更高融合值；但融合仍然只是检索排序，并没有执行事实审核。

例如某段全文同时讨论 active power 和 reactive power，可能因词项或语义匹配进入前列。它是否支持“active power 是某种 reactive rating”，仍要审查句子关系，不能由排名替代。第 12 章的类别误判就是这种边界。

## 5.4 重排序和术语扩展为何没有成为默认

可选 reranker 使用固定 mmarco-mMiniLMv2-L12-H384-v1，int8 CPU、512 token、批量 2；只截断候选侧，过长查询拒绝。输出原始 logit，不是支持概率。固定候选池实验出现局部改善，也出现必要组合退步；关键已标退步不能统一归因于截断，因此没有采用为默认。

术语扩展实验及 27 条补标后的对称回算显示 BM25 局部收益，没有改善最终完整依据指标，保留基线。正文优先、编码核查等都是独立历史实验，不应因为代码存在就称当前服务已启用。这里记录的是具体报告的取舍，不主张 BM25 永远优于 Dense。

| 路径 | 当前状态 | 与事实审核的关系 |
|---|---|---|
| BM25 + 有界上下文 | 当前服务默认 | 提供候选依据，判断仍在审核层 |
| E5 Dense / RRF | 可选实现和历史实验 | 不自动替代默认，不表示语义正确 |
| 术语扩展 | 实验结束，未采用 | 相关性局部改善不等于完整支持 |
| 固定 reranker | 实验结束，未采用 | logit 不能作为可信总分 |

本章依据：`rag/bm25.py`、`rag/embedding.py`、`rag/semantic.py`、`rag/reranker.py`；报告索引见 `docs/documentation-index.md` 的检索实验表。手册编写没有重跑这些实验，也未下载模型。

## 5.5 BM25公式和三个因素

令查询去重词项集合为Q，语料有N个候选片段，df(t)为含词t的片段数，tf(t,d)为该词在片段d中的次数，L(d)为分词后token数，avgL为平均token数。本项目实际公式为：

```text
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(d,Q) = sum over t in Q:
  IDF(t) * tf(t,d) * (k1 + 1)
  / [tf(t,d) + k1 * (1 - b + b * L(d)/avgL)]
k1 = 1.5; b = 0.75
```

TF提高意味着词项多次出现，但分式趋近k1+1，收益饱和，不是出现两次就两倍分数。IDF让稀有词通常贡献更大；这里ln-positive-idf即使词遍及全部片段仍为正。长度归一化降低长文仅因有更多词而占优的倾向；b=0不考虑长度，b越大长度作用越强。

长度是实际tokenizer产生的token数，不是原文字符数。中文单字加双字会影响长度，不能拿英文词数公式直接代替中文分词结果。查询重复词去重，不引入额外query-TF倍数；空查询或平均长度为零时返回全零。

## 5.6 小型BM25排序手算

以下四个英文片段是教学构造，不是知识库或新实验。查询只有voltage，N=4，df=4，avgL=3.75，IDF=ln(1+0.5/4.5)≈0.105361。

| 片段 | token序列 / 长度 | tf / score |
|---|---|---|
| D1，document_id=z | voltage voltage control / 3 | 2 / 0.160856 |
| D2，document_id=c | voltage control current / 3 | 1 / 0.115781 |
| D3，document_id=a | voltage current current current current current / 6 | 1 / 0.082961 |
| D4，document_id=b | voltage control current / 3 | 1 / 0.115781 |

D1分数最高，尽管document_id=z仍排第一，说明身份不是主排序。D2和D4完全平分，假定其他键一致，b先于c，所以D4在D2之前。最终D1、D4、D2、D3。D3虽身份最小，却因长度惩罚得分最低；D2和D4相同正文仍可有独立来源身份。

代入D1的TF因子：5/[2+1.5*(0.25+0.75*3/3.75)] = 5/3.275≈1.526718；乘IDF得分。保留小数仅为解释，源码排序使用未四舍五入的float。实际平分必须是分值相等，不能自行设“相差很小就平分”。

## 5.7 E5输入、池化与余弦

实际编码器拼接 `query: `+查询或 `passage: `+片段，例如query: voltage control与passage: reactive power supports voltage。前缀不改写Evidence原文；tokenizer检查前缀边界，空文本拒绝，query超512 token拒绝而不静默截断。passage长文本按480/448窗口处理。

模型输出hidden的形状为batch×tokens×384。attention_mask=1的token参与均值，padding=0被排除：m = sum(mask_i*h_i)/sum(mask_i)。当前实现也包含非padding的特殊token/前缀位置，不另设正文专用mask。每份文本的窗口池化向量等权平均，再u=m/||m||2；非有限值或零范数触发ContractError。

用二维教学向量代替实际384维：两个有效hidden为(2,4)、(4,4)，平均m=(3,4)，L2范数5，u=(0.6,0.8)。padding即使有其他值也不计入。另一文本v=(0.8,0.6)已归一化，cos(u,v)=u·v=0.48+0.48=0.96。

一般cos(q,d)=(q·d)/(||q||2*||d||2)，两者都L2归一化后可直接点积。这个0.96是教学相似度，不是事实支持概率。当前默认API没有启用Dense；这段说明解释已存在的可选编码与搜索实现，没有调用模型或重建向量。

## 5.8 RRF公式与两路手算

RRF(d)=sum over lists j: 1/(60+rank_j(d))，名次从1开始，未进入某路候选就没有该路贡献，不能当成rank=0。当前等权，两路候选各截到50，再融合后取需要的结果；不混合BM25原始分值和余弦尺度。

| 片段 | BM25名次 / Dense名次 | RRF分值 |
|---|---|---|
| A | 1 / 4 | 1/61+1/64≈0.032018 |
| B | 2 / 1 | 1/62+1/61≈0.032522 |
| C | 3 / 2 | 1/63+1/62≈0.032002 |
| D | 4 / 3 | 1/64+1/63≈0.031498 |

融合排序B、A、C、D。B在两路都靠前，得分最高；A与C很接近，但A略高。这是名次算术，不需要再次编码。平分仍按固定身份键，保证同样输入可复现。

## 5.9 为什么完整组合反而退步

假设回答需要B提供条件、C提供结论，必要组为{B,C}，只取top2。Dense的B、C满足完整组合；融合后B、A让C落到第三，组合覆盖由2/2降至1/2。A可以很相关，但并非C的替代证据。RRF逐片段融合，不以“满足必要组合”作为优化目标，所以局部名次收益与完整依据收益可以相反。

这个手算仅说明可能机制，不推断历史模型内因。项目历史术语扩展/重排序报告另有实际组合退步证据，应查固定候选、截断和标注分母；不要拿教学例子宣称已解释每个真实退步。

# 6. 版本、引用、快照与严格类型依据

## 6.1 不同身份回答不同问题

文档身份回答“哪份资料”；派生版本回答“哪次解析和切分”；knowledge_version 回答“哪个固定知识快照”；evidence_id 回答“哪份可回查依据对象”；quote_id 回答“这次候选中的哪段引文”；answer_id 与 answer_version 回答“哪个回答的哪一版”；claim_id 与 finding_id 回答“审核目标与判断是哪条”。这些字段不能混用。

字符区间只有放回指定版本全文才有意义。相同文字出现在两个页或两个回答版本里，身份仍可能不同。程序定位使用实际字符串与区间，不允许模型凭记忆提供似是而非的 offset。生成回答的 answer units 也由程序计算范围，避免让模型猜测全文位置。

## 6.2 严格类型依据

| 审核目标或依据类型 | 可以支持的判断 | 不能偷换成什么 |
|---|---|---|
| text_excerpt | 技术事实与具体原文关系 | 元数据、相似度或仅标题 |
| metadata_reference | 登记字段或来源质量描述 | 已人工核对官方正文 |
| input_snapshot_reference | 输入中是否提供指定信息 | 未交付全文的完整覆盖 |
| answer_text_reference | 回答确实写了某句或限定范围 | 该句在世界中为真 |
| calculation_result_reference | 已执行、成功且绑定本 claim 的有限计算 | 任意其他 claim 的结果或工程仿真 |

`core/typed_evidence.py` 及作用域校验把这些关系变成程序约束。引用原文必须精确匹配允许的候选，未知 ID、错范围或跨版本依据不能进入结果。请求内的 wire ID 可带命名空间，以避免不同批次对象碰撞；回查时应使用服务保存的正式身份。

## 6.3 原引用与独立检索必须分开

原引用审核问“回答引用的这段来源是否真的支持对应单元”；独立检索问“当前知识快照有没有其他支持”。独立找到正确资料，不能回头证明原回答那条引用也正确。用户参考、登记元数据、网页标题与官方正文同样不是等价对象。

在真实问答历史中，事实主张可以得到独立支持，同时原引用覆盖仍有警告。这是两种审核义务，而不是服务自相矛盾。界面分别展示角色，不把一个 evidence_id 列表全部归为“原引用已验证”。

## 6.4 提取忠实性与事实真值

faithful 表示提取目标忠实于回答；supported 表示对目标给定依据的支持关系。回答原本说“四类”，提取器必须保留这个断言，然后由事实审核判断其真假。若把错误目标改成别的命题，模型可能正确审核了错误对象。

程序能要求 fidelity 类型、义务和依据一致；disputed 或 mismatch 时不能假装完成事实支持。但模型自报 faithful 仍可能语义错误。第 12 章 N12 案例说明：上游把技术断言错分为 answer_scope，后续合法 supported 只证明回答写了这句话，并没有证明技术内容。

## 6.5 快照兼容与历史保存

历史结果应按它当时的知识、协议和提示解释。新 checker 出现后，不重新写旧记录使它看似通过。归档中应保存配置/版本哈希、原始响应索引及失败矩阵；公开说明仅引用必要内容，不复制私有响应。当前默认知识版本在 `backend/config.py`，完整值以冻结计划为准。

代码入口：`core/models.py`、`core/typed_evidence.py`、`services/text_location.py`、`services/answer_units.py`、`services/scoped_candidates.py`、`services/evidence_scope.py`、`services/answer_anchors.py`。阅读时选择一条 finding，逆向查到 claim、回答版本、typed basis 和原文，是最有效的练习。

# 7. 工具、预算、超时和取消

## 7.1 有限工具能够确定什么

SI 标量换算工具能确定已知单位比例，例如 230 kV = 230000 V。它不判断系统额定电压是否可接受，不补造标幺基准，也不执行工程仿真。工具结果必须成功、注册在本运行并绑定具体 frozen claim；模型不能拿另一个主张的计算结果作为自己的依据。

程序还有数量/枚举与结构化输入单位检查。当前 schema12 相关数量路径会将指定 v1.2 检查提升为 v1.3 的封闭正向声明语法；不因否定、转述或模型角色标签就认定数量断言成立。语法识别不了的文本报告 incomplete，而不是强行给出全局正确或错误结论。

## 7.2 程序规则与模型判断并列保存

假如模型把“类别数量为四”判为 supported，而程序在限定语法中观察到仅三个 rating 项并产生 warning，两个结果都保留。warning 不被包装成模型正确识别。相反，规则显示一致也不能证明模型理解了类别成员关系；规则只覆盖其显式语法。

自由文本没有结构化 quantities 时，输入单位检查会说明未完成完整单位审核。项目不能从一句概念回答虚构电网数据填入工具，也不能为了得到 completed 而把缺失输入默认成零。

## 7.3 服务端预算是权威

| 预算项 | 当前默认值 | 工程意义 |
|---|---|---|
| 模型请求 | 40 | 格式纠正和失败尝试也占用 |
| Revision | 最多 1 次 | 防止无限自我修订 |
| 总时长 | 800 秒 | 整个运行的截止时间 |
| 单步时长 | 110 秒 | 不超过剩余总预算 |
| 瞬态自动重试 | 0 | 不暗中重复付费请求 |
| 累计检索字符 | 160000 | 控制上下文交付量 |

更细的工具/检索上限见 `harness/contracts.py`；模型适配器自身还有请求超时、输出 token 和响应字符约束。浏览器不拥有调整这些上限的权力。真实验证时若采用独立预算，必须冻结记录并区分默认配置，不能把临时验收设置说成日常默认。

共享 ModelBudget 在实际尝试前扣计数，通过运行上下文作用于双审及格式纠正。若两个分支并发，记录完成顺序不一定等于 call number；统计应使用真实请求编号和 usage，不能仅按列表位置假设。

## 7.4 取消为何不是立即停止一切

取消是合作式信号。Harness 在阶段和受控调用边界检查状态，远端已经接收的模型请求未必能撤回。异步超时也不能物理杀死所有底层线程。AsyncSQLite Retriever 使用受控工作线程，取消包装等待不表示线程工作已结束，资源排空后才能关闭或复用。

因此页面先显示“已请求取消”，等待服务确认实际终态；不能仅凭按钮点击就显示 cancelled。已经有效保存的部分结果仍可回查。超时、网络失败、取消和 interrupted 分别记录，不合并成“资料不足”。

本章依据：`tools/unit_conversion.py`、`tools/scalar_numbers.py`、`services/quantity_checks.py`、`harness/contracts.py`、`model_adapter/runtime.py`、`harness/retrieval.py`、`rag/retriever.py`。工程上重要的是受控资源和失败可解释，不是承诺瞬时取消。

# 8. 有限修订与完整重审

## 8.1 为什么不能把 Revision 当成纠错保证

Revision 模型收到初审发现后，可以尝试最小修改，但也可能保留错误、引入新主张或省略限定条件。因此修订后的文本不是自动通过的结果。当前政策最多允许一次修订，新版本必须重新提取并完成事实与领域双审。

LimitedRepairPolicy 只对已观察的矛盾、证据不足、领域 warning 或程序 warning 提供有限修订机会。必要审核有执行问题时，不绕过它们去制造闭环完成。缺失工程检查仍保留，修订不能凭空获得厂站参数或仿真结论。

`harness/policy.py` 的方法内实际摘录如下；base 是此前基础政策计算的决策。这条提前返回让执行问题保持优先，不因后面存在可修复发现就继续修订。

```python
if verification.execution_issues or domain_review.execution_issues:
    return base
```

## 8.2 每个 finding 都有动作记录

`bounded-revision-v2-per-finding-actions` 要求冻结的事实与领域发现逐项交代 modified、retained 或 unresolved，并保留身份关联。至少存在真实 modified 且回答发生变化，才能构成有效修订。某条写成 modified 也不等于它已解决，最终解决状态只能从重审判断。

| 动作 | 表示什么 | 重审还要检查什么 |
|---|---|---|
| modified | 回答对该问题做了实际修改 | 是否改对、有无新主张 |
| retained | 保留某项内容或限定 | 保留是否合理、是否仍未解决 |
| unresolved | 无法用当前输入解决 | 是否需要人工补证据或前提 |

动作记录是一种账目完整性，不是正确性证明。它让用户看见“改了哪条、没有改哪条”，避免模型只写一句“所有问题已修复”而无法核查。retained 的问题也可能在 unresolved 输出中继续出现，不应因措辞温和而消失。

## 8.3 一次修订后必须终止

重审可能发现新问题，当前基线不允许继续第二次 Revision。终止时保存未解决 finding 和原因，交给人工。只有这样，模型请求预算和用户预期才能被界定；不断修到 pass 会隐藏失败并使真实验证不可比较。

真实样例中，230 kV 换算被改正，新增“并非230 V”却仍被事实模型判为证据不足。由1 kV=1000 V可知230 kV=230000 V，当然不等于230 V；这里没有数学争议。问题是该轮模型对否定比较要求确切绑定依据、未接受现有表达，属于审核行为及目标/依据绑定限制。该模型标签保留用于研究，不能改写成数学上无法确定。用户可以针对 v2 的具体 finding 追加意见，模型判断仍留在原记录中。

## 8.4 分阶段读取闭环

阅读 `harness/runtime.py` 时，先识别各轮 answer version 和 revision_round，再看提取、双审、policy、revision 的连接。不要把同一个 run 的 v1 与 v2 findings 混成一张没有版本的表。也不要把历史“事实阶段独立测试”称为全闭环测试，它可能根本没有执行 Generation、Revision 或 DomainReview。

观察一个运行可按四个问题展开：初审是否形成有效发现？政策依据什么选择 revise？修订动作是否覆盖冻结问题？新版本是否完整重审且保留未解决项？第 11 章用同一个真实 run 逐项回答；历史闭环失败在第 12 章保留。

代码入口：`harness/policy.py`、`harness/runtime.py`、`agents/revision.py`、`agents/revision_contract_v2.py`。不要把提示词中的“请修复”当作流程保证，应检查程序是否要求重审和终止。

# 9. 本机 API、队列、事务与重启

## 9.1 API 是受控视图

浏览器获得的是服务投影的运行状态、结果、trace、Evidence 和反馈，不是任意读取本机文件的入口。输入模型禁止额外字段，服务端保持预算、索引路径、数据库路径和政策权威。提交 mode 为 question_answer 或 assess_existing，已有回答模式必须提供实际文本。

| 接口类别 | 操作 | 主要约束 |
|---|---|---|
| health / capabilities | 查看服务模式与可用能力 | 不泄漏密钥或私有配置 |
| POST runs | 新建任务 | 鉴权、字段与长度校验、队列容量 |
| GET state / result / trace | 查询已知 run | 即使未结束也显示有效部分 |
| GET evidence | 原文与依据回查 | 必须属于当前运行作用域 |
| POST cancel | 请求取消 | 以实际状态确认终态 |
| GET / POST reviews | 查看或追加人工意见 | 实际回答版本和 finding 关系 |
| runs/page/{offset} | 固定大小运行列表 | 分页，不要求客户端读数据库 |

此表按职责归类，精确路由签名以 `backend/api.py` 为准。反馈或证据不能仅验证某个 ID 存在就放行，还要检查它属于请求的 run、answer version 和 finding。

## 9.2 事务保存什么

运行存储 SQLite 使用外键和 WAL，检查点在事务中同时写事件、对象与最新状态。事件保留过程记录，快照便于当前查询；回答、Evidence、Claim 与工具身份有不可变约束，finding 的进度视图可更新但历史事件继续存在。

若 observer 写库失败，Harness 不应继续付费工作而假装能够归档；服务进入存储故障处理并停止接受相关工作。一个模型结果已返回不意味着持久化一定成功，必须检查写库边界。这也是为什么程序需要执行问题，而不能把一切归入模型业务结论。

## 9.3 重启不重发

启动恢复把未完成 queued/running 任务标记 interrupted，保存已有有效部分，不自动重发付费请求。已完成结果与人工反馈继续保留。服务使用 ProcessLease 限制同一运行库多进程打开，当前 uvicorn 单 worker，避免两个服务各自声称拥有同一个活动任务。

任务状态与阶段状态是不同对象。finished 表示运行终止过程正常结束，failed 表示执行失败，interrupted 表示进程恢复发现未完成；业务可能仍是 review_required。不要把 interrupted 翻译成“审核判定不可信”，它说明的是执行中断。

## 9.4 反馈是追加记录

确认、反对、待查和说明绑定实际版本与可选 finding。错误版本返回 409，不覆盖原模型判断。当前本机令牌不是多用户身份系统，意见来源必须保留为本机用户/AI 辅助用户监督；不能自动称专家复核，也不能直接转为训练金标准。

如果 POST 反馈超时，页面保留文本并说明未确认保存；用户先查询已有意见，避免因重试重复追加。只显示“网络请求已发送”不能被解释成“已保存成功”。

阅读入口：`backend/api.py`、`backend/service.py`、`backend/store.py`、`backend/local_access.py`。真实重启核验在 `data/runtime_local/v0.1-acceptance/real-restart-verification.json`，与离线恢复测试分别使用。

# 10. Web 界面、来源链接与中文解释

## 10.1 安全展示是不可信文本处理

回答、证据、模型原因和人工意见均可能含 HTML 或脚本样式文本。当前页面使用 textContent 和 createElement，不直接 innerHTML，也未引入 Markdown 执行或不受控 HTML 渲染。CSP 将脚本、样式和连接限制在同源；不开放宽泛 CORS。

访问令牌由用户输入，仅放页面闭包内存，连接后清空输入框，刷新重新输入。它不在 URL、localStorage、源码、截图或日志中。DeepSeek 密钥只由服务端既有入口加载，浏览器不知道它。两个凭据解决的问题不同：前者访问本机服务，后者访问模型提供方。

## 10.2 来源 URI 的结构化投影

早期投影把宽泛“像路径的字符串”规则作用到来源 URI，合法官方 HTTPS 也被误隐藏。修复后对结构化来源字段使用 URI 解析规则：只接受公开 HTTPS，拒绝不适当协议、用户信息、私有或本机主机及不安全查询信息；未知来源保持空，不猜测。

模型字段中的敏感凭据和私有路径继续去除，但不能把 JSON 诊断位置 `$.findings[2].bases[0]` 当成本机文件路径。本轮真实批次完成并冻结后，单独修复 field_path 的投影误隐藏；没有在付费批次中途改代码并继续视作同一批。

外部链接只让浏览器打开来源，不由服务器自动抓取，也不附带本机 Authorization。页面设置 noreferrer、noopener 与 no-referrer。生成一个链接不等于已验证外站当前可达，也不等于它的全文支持当前主张。

## 10.3 中文摘要的四条轴

主区域分别显示运行终态、必需阶段完整性、必需检查是否全评估、业务决策与原因。摘要由实际结构化结果确定，不统一写成“资料不足”。执行错误、矛盾、证据不足、工程前提缺失和无法评估分别解释；原始英文原因及 JSON 保留在详情。

若下一步只知道某条 basis 不够，应提示查看该条 Evidence 或待人工检查；不能自动生成未经审核的电力操作建议。若结构化发现明确列出缺失前提，可说明需要补充该前提以供评估，仍不推导具体工况值。

## 10.4 防重复付费提交

按钮锁定防止重复点击。提交响应丢失时，任务可能已经存在，因此页面显示状态未知并先查询运行列表；不能因为 POST 超时自动重新提交。GET 网络断开也不证明任务不存在。页面恢复可使用 run_id，结束后停止轮询。

异步视图更新还需要代次标记：用户切换 run 后，旧请求返回不能覆盖新任务页面。服务模式变化时先停止并确认当前能力，不把 synthetic_fixture 结果显示成 real。取消仅表示已请求，最终状态等待服务确认。

本轮实际内置浏览器检查了中文摘要、合法来源链接、修订版本、Evidence、工具与反馈；截图归档不含令牌。危险文本、重复提交和错误响应还有离线/客户端回归，但这些测试不证明模型语义正确。

阅读入口：`backend/serialization.py`、`backend/presentation.py`、`backend/static/app.js`、`tests/test_v01_presentation.py`、`docs/local-review-ui-v1.md`。

# 11. 一次真实服务修订：逐阶段阅读

## 11.1 冻结输入与验证目标

唯一真实验收 run 为 `e1c6bc1336cd4c89acee8bd2795a0ebb`。它是构造的标量换算开发样例，明确不是厂站数据。通过浏览器调用本轮 API，现有真实装配和 Harness 自主执行，不在 evaluation CLI 中拼接结果，也不强制修改政策触发 Revision。

问题：请检查这个电压单位换算是否正确，并在必要时给出最小修订。

冻结已有回答：`230 kV equals 230 V.`

预期检查点是初审能否识别千倍换算错误、原政策是否决定一次修订、新版是否重新提取和双审、Evidence/工具/反馈是否绑定实际版本，以及重启后是否保留且不重发。预期不要求 final pass，也不把正确换算外推为工程安全。

## 11.2 预算预检为何先停止

最初授权最多 30 次，预检推导最坏结构为 14+C2，其中 C2 是 Revision 后原引用单元数。协议没有小于剩余预算的硬界限，因此在提交前停止，并保存预检。用户之后明确撤销上限，另建冻结计划，不能把早期停止记录删掉。

新计划按单响应最多96000字符、每个非空引用单元至少一个字符，保守取14+C2≤96014，只调整该历史验收的模型调用预算。**96014是临时异常配置，不是推荐运行方案。** 默认服务一直保留40次，其他时间、检索、纠正次数、模型与政策未改；实际只有8次。

截至本次源码核对，根本设计缺口尚未修复：Revision answer_units及原引用绑定没有与审核成本相匹配的小型显式数量上限，仍不能用40证明任意合法修订都能完成最坏引用审核。全局40请求上限仍保护费用，耗尽就停止并保存部分结果；它保证有限调用，不保证所有必需阶段完成。移除临时大预算或恢复默认不等于修复了这个协议缺口。

设计教训是“受控成本上限”和“最坏情况下阶段完整性”需要分别证明。未来可独立设计引用单元上限及成本预检，再验证其与审核义务一致；本轮没有实施这些修复，也不为赶预算跳过检查。

## 11.3 初审和一次 Revision

初审事实 finding 判定 contradicted，领域回答单位项给 warning；SI 工具计算 230 kV = 230000 V，结果绑定该冻结主张。LimitedRepairPolicy 因观察到可修复问题决定 revise，没有跳过缺失工程检查。

Revision v2 的实际文本为：“最小修订：230 kV 等于 230000 V（1 kV = 1000 V），并非 230 V。该修订仅针对所给标量电压单位等式；未运行任何仿真或工程计算，不构成完整单位审核或工程安全结论。”

逐 finding 动作覆盖初审一条事实和六条领域发现。换算/回答单位被修改；缺工程输入、完整单位审核、仿真等问题仍 unresolved，范围限制和操作前提边界保留。动作账目不自动将这些未完成项目变成 completed。

## 11.4 重提取与双审的有效结果

| v2 主张或限定 | 事实结果 | 应怎样理解 |
|---|---|---|
| 230 kV 等于 230000 V | supported | 有对应标量工具依据 |
| 1 kV 等于 1000 V | supported | 有对应比例依据 |
| 并非 230 V | insufficient_evidence | 数学上成立；模型未接受对应否定比较的绑定依据，检查审核行为 |
| 仅讨论所给标量等式 | supported | 回答范围锚点，不是外部事实证明 |
| 未提供/未运行仿真 | supported | 输入快照及范围，不证明工程已分析 |
| 不构成安全结论 | supported | 回答限定，不是工程安全判断 |

共六条，五条 supported、一条 insufficient_evidence。必需阶段完成，但领域必需检查没有全部评估；最终 review_required，执行问题最终列表为空。这些状态不矛盾，不应写成“全部可信”。

## 11.5 真实结构失败与唯一纠正

首次事实重审把另一个 frozen claim 的计算结果绑定给当前 finding，程序拒绝，诊断为 `calculation belongs to another frozen claim`，位置 `$.findings[2].bases[0]`。五条有效 peer 保留，错误条不凭空补齐。阶段级唯一格式纠正后，响应形成合法对象。

原失败响应、纠正响应和检查信息都保留。最终阶段成功不表示从未失败；结构纠正成功也不能解释为模型已正确审核该否定比较；数学等式本身并无争议。该剩余问题作为人工待查反馈绑定 v2 实际 finding，原模型判断不覆盖。

# 12. 历史失败：契约修复与语义边界

## 12.1 模板冲突不是模型一个人的错

历史独立事实审核曾继承联合输出模板，系统示例要求 findings+citationreviews，而请求希望独立阶段根结构。模型返回混合根结构，程序拒绝。此时只说“模型不听话”会掩盖提示设计冲突；根因包括模板复用不当。

schema12 配套 standalone templates 分开了独立任务，只共享公共约束，配合更严格目标与依据校验。验证仍需检查实际响应和纠正，而不是仅证明提示里删了一个字段。历史 v2 曾有初审、Revision、重提取及领域阶段成功，但事实重审 0/2 完成，不能写成完整闭环 2/2 成功。

## 12.2 数量与类别的语义漏检

“四种 rating”案例中，模型把包含 active power 的列表作为支持，即使类别数量和成员关系有问题。程序在有限语法中可以对显式数量与完整列表比较，产生警告；但这不是模型正确识别了错误，也不能证明所有自然语言枚举都可机械解析。

现有数量规则逐步收紧：拒绝含混列表、否定或转述上下文，不自动把 power output 计为 rating 类别。输入格式超出识别范围时 incomplete。规则精确度改善不能被扩写为模型语义能力改善。

## 12.3 N10、N11、N12 的不同失败

| 开发组件例 | 实际观察 | 正确报告方式 |
|---|---|---|
| N10 | 将提取忠实性与类别真值混淆，合法 not_assessable | 没有完成预期数量错误识别 |
| N11 | 纠正后仍返回非法 dimension，执行不完整 | 执行失败，不是合法业务不确定 |
| N12 | 技术主张上游分为 answer_scope，纠正后 supported | 合法结构仍可能审核错误目标 |

该阶段是冻结主张的事实组件测试，不是 12 个完整服务闭环；10 个 synthetic fixture 与 2 个真实资料开发例，不是独立专家验收集。历史报告中 12 个数量组件只有 11 个完成执行，N11 保留失败；不能删掉失败只计算成功响应。

## 12.4 单位格式修复的边界

单位工具曾对 ASCII 逗号分组作局部规范化，使 230,000.0 可解析，同时拒绝错误分组和虚假后缀。规范化仅在解析器内部，不写回原文 Evidence。修复能够证明受支持语法的计算稳定，不证明类别判断或工程适用正确。

类似地，标量 230 kV 换算成功，并不完成自由文本所有单位检查；缺少 quantities 时应报告不完整。一个过度积极的界面可能把工具成功显示成“工程校核通过”，所以 v0.1 专门分开模型、程序规则、工具与执行完整性。

## 12.5 失败分析的写法

一个可复查的失败条目需要：冻结输入、当时版本、原始响应索引、失败字段、有效部分、原因假设、程序修复、回归结果和剩余语义问题。原因假设应区别已证实与待查；不能仅凭一次模型输出断言模型内部推理机制。

例如本轮 field_path 被误隐藏是服务投影缺陷，有代码与回归定位；“并非 230 V”未被支持是模型/依据绑定行为，当前任务没有做模型语义专项修复。把两者混成同一种 bug 会导致无谓重跑，甚至中途改协议后把不同批次拼接为成功。

依据：`docs/review-reliability-v2.md`、`docs/fact-rereview-v3.md`；私有逐条报告见 `data/retrieval_local/deepseek/reliability-v2/`、`fact-rereview-v3/`。这些历史失败没有被新手册或 v0.1 成功样例覆盖。

# 13. 测试、检索指标与监督标注

## 13.1 测试对象和结论分开

当前最终离线验证为 428 项通过，日志记录耗时 45.986 秒。这是当时最终源码的离线程序验证，不是 428 个独立真实模型案例。手册与上传阶段没有重跑历史实验，也没有新增模型请求；文档变动不把测试证据改称新执行。

假组件可以确定性覆盖队列、状态、取消、部分结果、版本、反馈 409、401、恶意文本、来源安全和恢复行为。真实模型验证则覆盖提供方协议与实际语义行为，但样本有限。两类应并列报告，不能用多写几百个假断言替代真实语义评测。

## 13.2 指标究竟数什么

| 指标 | 本项目定义要点 | 常见误读 |
|---|---|---|
| Hit@5 | 前五是否有 grade≥2 | 至少一段相关不等于完整答案依据 |
| MRR@5 | 首个 grade≥2 的名次倒数 | 后续必要片段完全缺失仍可能很高 |
| judged-pool Recall | 命中已标核心正例 / 已标候选池核心正例 | 不是全语料 Recall |
| nDCG | gain=2^grade-1，按名次折扣 | grade1 背景贡献不等于直接支持 |
| 必要组合覆盖 | 某个替代组是否所有成员齐全 | 命中最多成员不等于完成一组 |
| 范围内完整依据 | 有适用标注与完整必要组 | 不是回答正确率或安全认证 |

无正例时某些指标没有定义，不能擅自把 undefined 混入平均当零；报告需写 valid n。Hit/MRR 的处理与 Recall/nDCG 的有效分母也不是完全相同，精确行为以 `evaluation/supervised_retrieval.py` 为准。

## 13.3 unknown 保留排名

未标片段保留真实名次，标为 unknown，不能当不相关删除后重排。否则一个未知的第一名被移走，已标正例从第五名变第一名，指标会虚高。相邻未标上下文同样保留未知，补充跨问题标注不插入本次检索排序制造命中。

必要证据可能有多个替代组合。应分别报告最大成员覆盖比例和是否至少完整覆盖一个组合。只召回三项中的两项可能对解释有帮助，却不能称已满足完整依据。问题还需具备 answerable_with_scope_limits 等资格，不能对标注为 partial_not_sufficient 的问题乱算完整支持。

## 13.4 标注来源和泄漏

当前标注是 AI 辅助、用户监督，不是独立专家金标准。曾看到已有候选或答案建议的冻结家族，不应包装成严格盲测。开发/冻结家族分开有助于减少同族泄漏，但不自动抹去此前暴露。

语言、自然问题/关键词、问题家族需分别汇总；同一概念换几种问法的样本相关，不能简单当许多独立问题。家族宏平均用于减轻某族数量较多的影响。反馈来源也需保留，确认意见不是自动高质量训练标签。

## 13.5 一个指标改善后应追问什么

先看分母与 unknown 是否变了，再看是否只在开发问题改善，最后看完整必要组合有没有退步。术语扩展的局部 Hit 改善未形成完整依据收益，reranker 局部提升伴随组合退步，这正是未采用的理由。没有必要为了漂亮分数重跑直到找到有利配置。

依据：`evaluation/supervised_retrieval.py`、`evaluation/term_supervised_final.py`、`evaluation/reranker_report.py` 及文档索引中的监督评测报告。源码、标注和实验是不同证据，面试时应说明它们怎样共同限制结论。

## 13.6 unknown下的Hit/MRR界限

前五名为[A未知，B背景grade1，C已知相关grade2，D未知，E已知不相关grade0]。不删除A/D，不压缩名次。数学上已有C在前三，真实Hit@5必为1；MRR最低1/3，若A补标为相关则最高1，所以MRR∈[1/3,1]。这是在保留排序条件下对未知标签的界限分析，不是将unknown记为0。

另一例前五名[A已知0，B未知，C已知1，D未知，E已知0]，没有已知正例：Hit@5∈[0,1]，MRR∈[0,1/2]。最乐观首次正例是第2名，不能把B搬到第1名算上界1；若所有未知最终不相关，MRR为0。

**实际评测器更保守**：`score_question.hit_rr`只要top5有unknown，就返回(None,None)，即使上例C已知相关也不输出确定Hit=1。聚合只统计非None，并报告有效n。本节界限是教学分析，没有新增评测字段、修改程序或重算历史指标；不能把界限替换成已报告的实测均值。

## 13.7 必要组合和unknown同时存在

保留第一例排序，已标必要组G1={C,F}，另一替代组G2={C,G,H}，F/G/H均不在top5。G1覆盖1/2，G2覆盖1/3；最大成员覆盖=1/2，any_complete=False。即使已知Hit为1，也不形成完整组。

若某个已登记组成员都在top5但其中有unknown，程序按ID计算组覆盖仍可能True，并另外列unknown_label_ids；这只表示组成员被检索到，不证明标签和支持关系已核实。范围内完整依据还受answerability、partial_not_sufficient等标注资格限制，更不等于生成答案正确。

分母是当前已标候选池；缺失知识库之外的资料或未标正例没有被凭空补进Recall。阅读报告时同时看unknown、有效n、必要组、标注资格，不能只挑一个Hit数字。

## 13.8 教学算例与实验的边界

本手册BM25、余弦、RRF和unknown例子都为小型构造手算，仅验证公式理解。复核这些算术不调用Retriever真实索引、不编码E5、不发模型请求，也不是新的检索实验。真正历史效果继续依据原冻结报告，不因本轮讲解而更新任何指标。

# 15. 技术取舍、旧项目迁移和后续微调

## 15.1 保留、改写、替换、弃用

| 项目要素 | 处理 | 原因与状态 |

`power-system-hallucination-risk-assessor/` 是独立旧仓库，当前不修改、不展开 Git 跟踪。旧项目的文档可以说明历史动机，但旧结论不自动升级为现有审核依据。手册编写和上传审计都没有遍历其内容。

## 15.2 为什么优先可回查而不是“智能总分”

综合分数容易掩盖哪条主张、哪种依据和哪项未完成检查。当前项目选择对象身份、版本、原文区间、typed bases 和追加反馈，让用户能看见结论的来源及失败。代价是显示更复杂，用户需要理解 supported、not_assessable 与执行问题的区别，因此 v0.1 增加中文摘要而没有简化成绿灯批准。

这不是断言分数永远无用。若未来有明确任务、专家标注和校准评测，可以独立研究概率或排序；在现有证据下，不应把相关性分值或规则票数称为可信度。

## 15.3 后续微调尚未实施

当前没有事实支持判断的训练管线。本轮留下 N10/N11/N12、否定比较、类别数量等失败素材，为未来研究提供候选，不等于已经获得可训练金标准。第一步应是专业核实目标和答案、来源权限与必要证据，而不是把所有用户确认反馈直接导入模型。

建议将样本拆成技术事实支持、提取忠实性、目标分类、依据类型、工程适用条件等任务，防止一个标签同时表达多种失败。记录输入、资料版本、模型版本、人工来源和争议；含私有厂站资料的案例先处理权限，不自动公开。

## 15.4 采用与停止条件

按问题族划分训练/开发/独立测试，避免同一事实换措辞泄漏。冻结测试不只看合法 JSON，还看 contradicted/insufficient/not_assessable 的语义、错误目标、缺前提及过度支持；保留有效分母和未知项。必须与未训练基线同条件比较，不只报告挑选后的改善例。

成本包括标注、训练、推理与维护。采用条件应在实验前定义：关键错误降低、未引入重要退步、权限满足、成本可接受；停止条件包括无法取得可靠标签、收益不稳定、工程建议误支持增加或预算超出。具体阈值尚未设计，也没有本轮授权执行新实验。

## 15.5 本机原型是否可冻结

具备冻结本机人工辅助原型的条件：统一服务、界面、持久化和一次真实修订已验证，剩余语义问题如实保留。不能宣称生产验收或安全认证。来源视觉未核对、工程前提缺失、模型目标误分类及样本覆盖有限，不阻断用户监督下的本机阅读与复核，但阻断自动采信和工程批准。

依据：`docs/legacy-migration-principles.md`、`docs/design-decisions.md`、`docs/fact-rereview-v3.md`、`docs/prototype-v0.1.md`。后续方案是建议与待授权工作，本手册交付不启动下一轮。

# 16. 面试问题、追问和回答证据

## 16.1 入门：用完整流程回答

**问题：PowerTrustAI 与普通 RAG 问答有什么不同？**

回答思路：先说明两个入口复用 Harness；回答冻结后提取主张，事实与领域双审，typed bases 回查，确定性政策决定最多一次修订，保存版本与人工反馈。不要只说“用了四个 Agent”。普通检索生成是其中一段，项目还处理运行完整性、失败与恢复。

追问：证据检索命中就表示回答正确吗？答：不表示；BM25/Dense 只产生候选，原引用和独立证据分别审核，模型仍可能把相关内容误当支持。证据入口：`backend/assembly.py`、`harness/runtime.py`、第 12 章类别例。

**问题：为什么叫 OfflineHarness，还能调用真实模型？**

回答思路：名称沿用离线工程抽象，真实组件通过注入装配，演示与真实复用调度而非复用结果。强调 synthetic_fixture 标识和真实配置失败不偷偷回退假组件。追问可展示 factory 与 ServiceConfig，不拿假响应证明真实模型能力。

**问题：ClaimExtractor 是第五个 Agent 吗？**

回答思路：本项目将四个有名称的 Agent 与提取服务分开；职责比数量重要。提取器建立目标与义务，Harness 控制流程，不参与自由模型投票。追问：提取错了怎么办？说明 fidelity 程序检查与 N12 剩余语义风险。

## 16.2 中级：解释身份和数据边界

**问题：为什么需要 answer version，直接覆盖答案不更简单吗？**

回答思路：finding、Evidence、工具和反馈都要指向实际文本；修订改写后旧 offset 不能复用。保存 v1/v2 能复查改了什么，并防止反馈绑定不存在的版本。证据：`core/models.py`、`backend/store.py`、`agents/revision_contract_v2.py`。

追问：修改过的 finding 是否代表解决？答：动作只是账目，重审才产生新判断；真实 v2 仍有“并非 230 V”证据不足。不要说修改后自动 pass。

**问题：如何避免另一个运行的 evidence_id 被查询？**

回答思路：鉴权只是第一层，Evidence/反馈还要检查 run 作用域及回答/finding 关系。模型依据也要求 frozen claim 和版本相符。真实重审曾错用另一个 claim 的计算结果，程序拒绝，说明身份校验能够实际阻断一种错误。

**问题：为什么不直接 innerHTML 展示模型 Markdown？**

回答思路：模型与用户文本不可信，首版纯文本满足功能，textContent 配合 CSP；若未来支持 Markdown 必须独立安全处理，不能以模型“不会生成脚本”为保证。来源 URI 也按结构化协议、主机与敏感信息验证。

## 16.3 进阶：成本、并发与恢复

**问题：如何证明不会无限调用模型？**

回答思路：服务端共享请求预算、每阶段最多一次格式纠正、Revision 最多一次、无瞬态自动重试、总/单步超时；实际尝试计数而非只数成功。最坏预算要包含引用单元扩展，本轮 30 次预检因 C2 未严格界定而停止，后来另获授权冻结，不隐藏这个事实。

追问：用户说预算无限就不需要限制吗？答：仍需要结构上界、时间预算和停止条件；授权放宽费用不意味着可以改协议或无限重跑。证据：冻结计划、`model_adapter/runtime.py`、`harness/contracts.py`。

**问题：取消为什么还要等待服务确认？**

回答思路：远端调用已发送与底层线程都未必可物理取消，页面只申请取消，Harness 合作式检查，保存有效部分。资源关闭前排空，不能把 async task 被取消误认作工作线程结束。

**问题：进程崩溃后怎么处理任务？**

回答思路：SQLite 检查点保存事件与对象，重启未完成任务 interrupted，不自动重发；已完成结果与反馈保留，同库 ProcessLease 限制多实例。代价是用户需要手动决定新运行，不能承诺 exactly-once 远端调用。

**问题：POST 超时如何避免重复付费？**

回答思路：客户端锁定，不自动重试；显示状态未知，查询 run_id/列表核实。当前不是跨系统幂等协议的普遍证明，网络恢复仍需用户监督；不能拿“按钮置灰”声称所有分布式重试风险都解决。

## 16.4 深入：指标与真实失败

**问题：428 个测试说明准确率很高吗？**

回答思路：不说明；它验证程序契约与行为，真实语义只有有限构造/资料案例。分开组件、全闭环、结构完成与目标正确。举例 schema12 合法 supported 可能因上游 answer_scope 分类错误而漏检技术事实。

**问题：Recall、完整依据和回答正确率有什么关系？**

回答思路：Recall 是已标候选池分母，必要组合表示若干互补资料是否齐全，回答正确率需要对生成内容另行标注。unknown 保留名次，undefined 的指标写有效 n，不能删除未知项优化排名。

**问题：为什么没有采用 Dense 或 reranker？**

回答思路：代码可选实现与默认采用不同，固定实验显示局部改善未稳定提高完整依据，reranker 有组合退步。当前保留 BM25 可追踪基线；不宣称技术路线永远优劣。追问可沿报告核查配置哈希、候选池、截断审计和分母。

**问题：说一个你能核查的失败和修复。**

回答思路：可以选择模板根结构冲突、跨 claim 工具引用或 field_path 投影。按输入→响应→失败字段→原因→修复→验证→限制说明。若尚未亲自参与，不编造个人贡献；表达为“项目记录显示，我可以解释和复现这一机制”。

## 16.5 高阶：诚实说明尚未解决的问题

**问题：双审是否能消除幻觉？**

回答思路：不能；职责独立但共享提取和提供方模型，错误相关。typed bases 限制可接受结构，不证明语义理解。人工复核和失败归档保留，未提供安全认证。

**问题：现在可以微调吗？**

回答思路：未实施训练管线；先核实人工标签与来源权限、拆分任务和问题族，再冻结独立评估与采用/停止条件。用户反馈来源必须保留，不能未经审查当专家标签。

**问题：这次真实 Revision 是否验收成功？**

回答思路：服务内链路与持久化验证成功，模型结果仍 review_required；5 supported/1 insufficient、工程检查未全评估、一次格式纠正被归档。足以说明本机原型的这个链路已跑通，不能外推到所有电力问题。

面试准备应先独立走一条 run，再用上述问题练习两分钟回答和五分钟追问。好的回答包含机制、一个真实例子、代码/归档入口和限制；不需要堆模型名称或夸大效果。

## 16.6 为什么没有使用LangChain

回答思路：当前直接Python协议、dataclass、适配器和受控Harness已经满足固定流程；已有严格ID/版本/typed-basis校验、预算和observer需要明确控制，引入通用框架会增加映射与迁移成本。当前依赖和调用路径没有LangChain，不是先使用再宣称卸载。该取舍说明项目规模与既有工程复用，未做框架性能对照，也不主张LangChain不适合其他系统。

追问“以后会不会用”：只有明确新需求且能保持契约、预算、回查与失败隔离时再评估，不能为使用框架重建第二套Harness。证据是assembly/runtime及依赖清单，不是虚构一个未做的benchmark。

## 16.7 受控工作流和自主Agent

当前阶段、工具、输入身份、最大修订及停止条件由程序定义。模型在阶段内判断支持关系、提取或改写，却不能自由增加目标、无限调用、替换数据库或自行批准结果。自主Agent通常允许模型选择更多行动与路径；项目没有将这种自治作为已实现能力。

追问“双审并行是否自主”：并发只是调度方式，仍是固定的两个review任务。角色名字不是自治程度。共享主张、同一提供方模型意味着错误相关，独立职责不自动等于独立统计样本。

## 16.8 async、线程和取消

async协程在await处让出事件循环，并不让同步SQLite或CPU代码自动并行。当前Retriever用单工作线程持有只读连接，避免阻塞事件循环及跨线程连接混用。asyncio.shield保护底层future：调用方取消等待时，线程任务可能仍在执行；active未结束前拒绝新工作，服务关闭先drain。

双审create_task/gather可以并发等待网络，但cancel()是协作信号。远端已接收请求未必撤回，线程没有通用安全强杀。追问应说明耗时边界、部分保存和资源归还，而不是承诺“取消瞬间没有费用”。

## 16.9 SQLite WAL和单进程限制

WAL把更新追加到日志，读取可保持快照；它不意味着多个写事务同时自由写。RunStore用短BEGIN IMMEDIATE事务保护event、snapshot与object一起保存，timeout=2；长模型调用发生在事务外。写入失败回滚并转StorageError，服务停止后续相关工作。

单worker与ProcessLease是当前应用队列/存储拥有者的约束，不是SQLite只能被一个进程读取。若直接开多个uvicorn worker，每个有自己的活动槽和内存队列，会破坏“一个活动运行”语义；WAL解决不了调度分裂。未来多进程需要单独的协调设计，本轮没有实现。

## 16.10 客户端锁不是服务端幂等

posting/uncertainPost仅约束当前页面；两标签页、HTTP客户端或刷新后仍可各自POST。服务每次有效提交生成新run_id，当前没有按幂等键在服务端去重并返回同一已存在任务的协议。所以按钮锁不能证明exactly-once，也不能覆盖“服务器已接受但响应丢失”的情形。

当前策略是不自动重POST，状态未知时核对列表/已有run_id，再人工决定。未来若设计幂等键，需定义请求指纹、原子登记、冲突与保留期限；即使如此远端模型请求的物理一次性还需单独分析。本轮只是解释限制，不新增幂等功能。

## 18.3 政策：修订机会不等于放行

```python
def decide(self, verification, domain_review, budget, revision_round):
    base=super().decide(verification,domain_review,budget,revision_round)
    if verification.execution_issues or domain_review.execution_issues:
        return base
    actionable=any(f.status in (VerificationStatus.CONTRADICTED,VerificationStatus.INSUFFICIENT_EVIDENCE)
        for f in verification.findings) or any(f.check_status=="warning" for f in domain_review.findings)
    actionable=actionable or any(c.status=="warning" for c in verification.consistency_checks)
    if actionable and revision_round < min(1,budget.max_revision_rounds):
        return AuditDecision(DecisionKind.REVISE,("One bounded repair of observed issues; incomplete checks remain unresolved; full re-review required",),
            "limited-repair-policy-v1",base.unresolved_finding_ids)
    return AuditDecision(DecisionKind.REVIEW_REQUIRED,
        ("Limited reviews completed or stopped; unresolved findings and unperformed engineering analysis remain; no safety certification",)+base.reasons,
        "limited-repair-policy-v1",base.unresolved_finding_ids)
```

输入：两个审核结果、服务预算、revision_round。输出：AuditDecision，不调用模型。base已考虑执行/工程完整性；执行问题提前返回。actionable观察矛盾、证据不足、领域或程序warning；min(1,预算)使有限修订不超过一次。达到限制或没有修订必要时仍review_required，保留base原因和未解决ID。

这段代码没有自动重跑与“修到pass”；模型格式是否合法由前面校验器负责。预算耗尽的执行问题不能通过调政策伪造完整审核。

    v=wire(snapshot);event=v['event']
    with self.tx():
        ordinal=self.db.execute('SELECT COUNT(*) FROM events WHERE run_id=?',(rid,)).fetchone()[0]+1
        self.db.execute('INSERT INTO events VALUES (?,?,?,?,?)',(rid,event['event_id'],ordinal,dumps(event),dumps(v.get('stage_output'))))
        self.db.execute('UPDATE runs SET snapshot=?,harness_state=? WHERE id=?',(dumps(v),v['state'],rid))
        # Bind domain finding IDs to this frozen answer; domain findings already have explicit bindings.
        self.index(rid,v)
        if v.get('stage_output') and event['component']=='evidence_verification':
            answer=v['stage_output'];aid=answer['answer_id'];version=answer['answer_version']
