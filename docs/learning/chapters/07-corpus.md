# 07 大语料：流式构建、去重、事务和稳定身份

## 是什么：把处理过程当可恢复事务

IndustryCorpus2不是一个能一次read_json放进内存的小文件。已有73片发布字节约40.64GB，70片Parquet元数据可读、14,336,177行；3片发布文件缺尾部，哈希匹配也不能把它们修造为可读。数据集Apache-2.0卡片不自动证明每条原出处权威。正文扩大概念覆盖，未知机构/URL/日期保持未知，不独自批准规范、设定值或工程保证。

Parquet列式存储可按batch读取。rag/corpus_build.py使用iter_batches(128)，每次只有小批Python对象常驻，SQLite缓存有限、临时数据落盘。磁盘不仅需原分片，还要正文、FTS、WAL和发布备份空间；“电脑32GB内存”不意味着库能全装进内存。

## 构建顺序与断点

先核对分片大小和发布SHA，再打开Parquet。完整分片跳过；未完成片从已提交next_row恢复，仍从原始绝对行号计数。不能把当前batch的i=0当原始行0，否则每批内部身份碰撞。原始行号不是去重后序号；即使重复正文不新建正文，也必须保留来源关系。

每批BEGIN IMMEDIATE后写正文、chunk、FTS、缺原ID身份及next_row，最后commit。中间异常rollback，断点和正文同退。故障注入到行130时，第一128行已经提交，第二批整批回滚；恢复后从128继续，最终260行身份连续且不重复。只提交断点不提交正文，会永久漏资料；先写正文后单独写断点，会重复入库。

## 精确去重与谱系

SHA-256(raw_text)索引判断精确重复，不依赖模型“看起来差不多”。同一正文规范记录保留一次，corpus_duplicates记录分片、原行、记录身份和canonical_id。相同正文不表示出版机构相同，原出处仍未知。近重复不是这里的自动去重目标，不能为了省空间删必要限定。

教学构造：A行“在C下成立”，B行完全相同，C行“总成立”。A/B可以精确合并正文但保留两来源；C哈希不同，必须独立保存。把空格归一也做去重，需要另一个规范化版本及原文映射，不能偷偷改raw_text。

## 异构schema与内部身份

中文已处理片有_id，英文剩余51可读片均没有。原代码row['_id']在首英文片KeyError；这不是下载不完整或模型错误。6108030兼容：存在非空原ID时保留；缺失时生成带命名空间的内部ID，输入为固定revision、分片路径、原始绝对行号。

```text
internal_id = "industrycorpus2:row-v1:" + SHA256(
  canonical_json([revision, shard_path, original_row_number]))
```

正文哈希另存。ID用于来源行定位，正文SHA用于内容校验，两者不能代替。corpus_identity显式original_id_missing=1，不说这是原出版ID。Evidence的quality_warnings显示原ID缺失及稳定内部身份。原中文身份、片段公式、去重和已提交断点保持不变。

## 唯一写者、WAL和崩溃

venv父进程和实际Python子进程是同一次逻辑启动，不能看到两个PID就认定重复写者。启动前检查实际命令与父子关系；构建还采用OS非阻塞文件锁，崩溃释放锁，残留锁文件不代表仍有写者。不要删除数据库/WAL来“解锁”。异常必须关闭连接，Windows文件句柄未关闭会导致恢复或测试清理失败。

WAL使已提交读与单写者协调，不提供多写者并行吞吐。BEGIN IMMEDIATE提前获得写锁避免读后升级失败。运行库与语料构建库是两份库，日常模型请求不该被大库长事务占住。

## 不可变发布：构建库不能直接服务

构建完成需核对所有清单分片状态、去重关系、正文SHA、片段区间/身份、FTS完整性和原文回查。发布通过SQLite一致备份生成新文件，写内容封印和数据库字节哈希。不能覆盖旧快照，更不能边构建边把“完整库”指向变化文件。排除坏片必须明确覆盖定义，不称全部发布字节都成功解析。

日常固定prefix-v2是153,088输入行、143,053唯一正文和326,565片段的部分快照，另保留可追溯旧资料。完整构建另行发布但不自动切换服务。新库没有对应向量索引时，只使用匹配的FTS/BM25，不复用旧向量冒充完整。

## 验证、坑与面试

验证应覆盖稳定ID、跨batch、事务回滚、重复来源、断点二次启动不增数、错误分片排除和不可变发布拒绝覆盖。生产当前进度以带时间的build-progress为准，书中历史数字不当实时值。

面试说法：“我把原始行身份和正文内容身份分开，精确重复保留谱系，每批数据与断点同事务。构建、发布和服务三阶段分离，未知出处明确标记。”追问为什么不直接从text_hash做内部ID：它会把不同来源行合并为同一来源身份，丢失谱系。

## 断点实验逐步推演

教学构造分片260行，batch128。事务1成功写0–127，next_row=128；事务2写128–129后在130抛异常，整个128–255批回滚，next_row仍128。恢复从原片读取，前128行跳过，继续绝对行128；最后256–259成功，next_row=260、complete=1。再次启动该片直接跳过。

若第259行正文与第0行相同，正文只新增259条，但输入身份有260条，重复关系有1条。不能以record_count=259认定漏了一行，必须同时查去重和输入进度。反之只有260条身份而正文/duplicate缺一条也不能叫完整。

最危险的恢复实现把offset先增加、再尝试事务；异常后继续使用已增加offset会跨过失败batch。当前过程把提交断点放事务里，异常退出并保留有效前缀。测试应真的注入中途异常，不只调用两次build检查一样。

## 稳定来源身份与文件哈希的分工

内部ID公式没有正文hash，是为了保留“原始哪一行”的稳定定位；正文hash另存用于发现内容变化。固定revision与清单文件SHA保证这次分片不能悄悄换内容。若有人改文件但保留名字，字节核验先失败，不会用同ID写另一正文。

原始_id可能为数字或字符串，保留str原值；None/空或列缺失明确缺失。不能生成一个看起来像原出版数据库编号的整数，读者会误认为官方ID。命名空间前缀让内部派生性质可见，quality_warnings保留事实。

## 为什么发布检查分层

构建检查文件和事务，发布检查全量正文/片段及FTS和成员，打开检查封印/结构，查询检查实际命中原文。每次查询扫描全部40GB既昂贵又没有必要，但完全取消原文回查会失去证据真实性。封印变化必须拒绝或显式重新验证发布，不能更新mtime后假装不可变。

学习站显示的进度是捕获时间，不做自动轮询写库。后台完成记录、publication manifest和日常配置是三件事；完整发布不等于日常已经采用，切换还需索引/知识匹配及用户使用验证。

### 自测1：缺_id为何不能造原出版ID？

::: answer 展开参考答案1

:::

### 自测2：行130异常为何回到128？

::: answer 展开参考答案2

:::

### 自测3：规范正文少于输入行一定漏库吗？

::: answer 展开参考答案3
不一定；精确重复有独立来源谱系，需联合核对。
:::
