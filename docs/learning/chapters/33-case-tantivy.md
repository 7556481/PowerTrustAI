# 33 案例：Tantivy：快读取为何没有快交付

配置见[当前状态](../../current-status.md)。本页解释项目记录，不声称项目所有者个人负责了所有步骤。个人发现、操作和决策经历需由本人确认。

## 从命中到模型：六个步骤分别量什么

以v28 Q1链为具体产品观察：SQLite首稿9.08秒、终态68.71秒；Tantivy首稿7.19秒、终态81.07秒。候选先交付初稿1.89秒，但终态反而晚12.36秒，不能只看检索/首稿。以下处理步骤是冻结v28实现的数据流，单次查询文本、单步时长与发送字符未在公开报告逐项列出，留作未知，不从中位数倒推。

|步骤|输入→输出|应核对的量与证据|
|---|---|---|
|90片召回|query→宽池6根|分片/映射身份、排名与读取墙钟|
|范围选择|父原文→连续包络/回退整段|父SHA、版本、start/end；摘取耗时|
|原文回查|派生ID→严格原文|逐字/hash一致，定位与邻接耗时|
|目的交付|根/邻接→生成/事实/领域目录|必要条件和预算内实际保留原文|
|消息构造|目录/回答→review_transport→客户端|证据字符与完整消息字符，不能拿索引大小替代|
|模型与交付|初检/纠正→终态API可读取|各角色完成、纠正、保存、100ms轮询边界|

报告中470个历史根全部回退整段、0摘短；并非摘取压缩成功。86对历史发送请求的主组证据205408→321547字符、完整消息1667021→2207415；这是离线历史请求分组统计，不能填作Q1本条真实消息长度。Q1实际调用7/8、纠正1/1、token166888/254826；调用多1并不足以证明增加12.36秒全来自它，也不能把token比值当延时比值。

## 怎样定位而不杜撰增时原因

先在同run/版本对齐dispatch、HTTP线程、检索返回与角色保存，再取最后完成路径；若模型响应等待包含在检索跨度内，不再相加。只有完整消息、单次响应和资源轨迹都齐，才比较输入体量或服务抖动等假设。公开报告未给出Q1每一阶段可分解秒数，教材不替它补造。

最终六完整对的两路终态中位29.99→37.60秒未过门槛，两路各7/8完整、失败保留。候选Q3和基线Q7事实失败不同，不能只挑成功快题；已有速度失败足以结束路线，质量逐句完整复核未证，不补跑。

::: answer 代码推演：读取少2秒，事实HTTP多5秒，领域最后完成，能断言终态多3秒吗？
不能。先确定这些区间是否在同一关键路径、是否被领域覆盖，再计算终态max。若领域结束一直最晚且其他不变，局部差可能完全被覆盖；若事实超过领域，才从新的最后结束算差。需要Q1本次各角色时刻，缺项保留未知。这里不能用四条宽查询1.87倍去填终态归因。
:::
