26 图编排、关键路径与资源所有权

本专题绑定应用提交 e4fb27e7c8893a5ad141ebef0ae5f32216648065，2026-11-24离线核对。配置只看当前状态。数字分别标记真实实验与教学构造；以下问题不授权现场工程操作。

四种Python对象怎样合作

先从一个小协程理解：async def read(): ...调用后得到协程对象，直接调用不会完成读取；await read()在当前任务等待；asyncio.create_task(read())创建另一个可被事件循环调度的任务。协程不是线程，若协程中直接执行长同步SQL，事件循环仍被堵住，新任务可能到SQL结束才获得运行机会。

线程池future则表示同步HTTP工作的执行状态。DeepSeekAdapter._executor.submit把_work交给线程；因此需要分开记录create_task、线程开始HTTP、响应结束三个时刻。早创建task的截图不能证明网络真的重叠。

实际图节点怎样更新状态

stage_node的关键路径：

execution = runtime.context['execution']
ended = await getattr(execution, name)()
return {'business_state': execution.state.value,
        'last_stage': name, 'next_stage': target}

运行上下文持有本次RunExecution，FlowState返回的是可路由的小状态。以revise节点为例，成功应用新版时target回extract_and_tools，未应用则END；merge_and_decide已结束则END，否则去revise。节点名字不是模型调用名单，prepare_review检索可能多步，事实角色也可能发多条原引用请求。

提前任务为什么必须有人收尾

prepare_review先完成事实输入并create_task；领域读取若抛异常，会cancel早期task并gather(return_exceptions=True)。review_pair成功时复用该task，避免同一初稿事实审核发两次。外层run也兜底处理未消费early task。gather回收异常不代表抹掉业务失败，报告仍要记录审核未完成。

try/finally保证即使中间raise也进入资源清理；上下文管理器把进入/退出动作配对。例子是Store短事务：正常退出commit，异常rollback；不是“with会自动修好失败”。Bundle.drain等底层_active完成，随后close释放资源；立即调用close不能撤回已发出的请求。异常应沿正确层传播：ModelTimeoutError、用户取消和Store写失败不能都转成“资料不足”。

题26.4：若事实协程已创建，随后一个同步检索占用事件循环4秒，最多能算提前4秒吗？

不能。先看线程真正启动时刻；若create_task后直到4秒检索结束才执行HTTP，则没有这4秒重叠。若检索经线程包装并让出事件循环，才可能在读取期间发HTTP。正式实现与旧实验应以同run轨迹核实，不由async函数名推断。接着用四种时间线判断最终谁最后完成。测试入口test_fact_domain_overlap_v23检查输入与失败收尾，真实提速仍只引用既有v23。

先区分图、业务对象与线程

LangGraph是阶段路由器；Harness与RunExecution持有单次业务运行、预算、证据及取消控制。线程是能执行同步HTTP或数据库工作的执行单元；asyncio任务是协作调度的协程，创建task不等于HTTP已在另一线程发出。 graph_runtime_v1的FlowState只有business_state、last_stage、next_stage；大业务对象在runtime context的execution里。七阶段复用RunExecution，checkpointer=None，禁远程tracing，不应宣称LangGraph提供业务持久恢复。

一次请求的边

validate_saved_inputs→generate或extract_and_tools；生成后提取/工具→prepare_review→review_pair→merge_and_decide；有资格才revise，新版回extract_and_tools。图不为业务节点自动重试，防止重复付费。顺序驱动保留相同阶段，供兼容/离线对照；切换必须显式配置，图依赖失败不会偷偷降级。

题26.1：overlap提前了什么？事实输入依赖领域材料吗？

prepare_review先完成事实目的检索，然后冻结事实证据、原引用和绑定，满足开关/模式/调用余量条件才创建早期事实审核。随后领域目的检索继续，review_pair复用早期事实任务并与领域审核汇合。事实证据不会被后续领域结果扩大，事实内部仍serial_v1。相关代码在prepare_review/review_pair，受管开关见managed。继续追问：只看create_task不足，须核对事实HTTP工作线程启动早于领域读取结束，旧真实轨迹与test_fact_domain_overlap_v23分别提供真实与离线层证据。

题26.2：领域检索失败时已经发送的事实请求怎么办？

异常分支取消early task并gather等待协程收尾；底层HTTP执行可能仍在进行，Bundle.drain观察资源_active直到完成，再close。完成、取消与释放不是同一个时刻。运行不能因事实部分结果有效就标完整审核。资源装配、execution.run及生命周期测试应一起读。继续追问：吞掉CancelledError会破坏取消语义；但立即关资源也可能破坏结算，因此清理需有明确所有权。

题26.3：两个10秒为什么不是20秒？

关键路径是决定最终结束时间的最长依赖路径。教学：事实输入t=2齐、HTTP持续10秒到12；领域读取2→6、审核6→11，则终态12；读取瞬间完成后仍由事实12决定，终态不变。若原先事实要到6才发，原终态16，提前可省4秒。必须在同一次运行的依赖图推导，不能把角色耗时相加。继续追问：预算不足、用户取消、阶段超时分别有不同原因记录；节省模型调用之外的检索并不必然缩短终态。
