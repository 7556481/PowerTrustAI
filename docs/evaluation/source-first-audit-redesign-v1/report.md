## 设计依据与实际变化

旧流程在每个回答版本重提取后，先做独立事实检索及可能的主体补检，再做领域检索；两个审核模型随后并发。schema13的独立事实与各原引用核验仍有各自范围。原文候选 literal_v1 可以在同次请求中评价全部原文单元、原引用及具体可修缺陷；source_actions_v2 已实现一次局部 Revision、重提取、完整双审和 Store 保存。历史给定合法发现修订4/4与自然N2/N4漏检分别保留。

新候选 `source_first_audit_v1` 复用上述原文/修订合同、四职责、Retriever单工作线程、既有FactRetrievalBinding、预算、确定性政策和LangGraph共享阶段。没有另建调度器或覆盖schema13；产品范围明确变为**资料忠实性与任务完整性审核**。提示单独版本化；领域仍承担适用性、输入、能力及安全边界。原引用来源与同源整合供给均不能冒充独立交叉来源。

`RunExecution.prepare_review` 从首次冻结生成交付快照取根片段。`AsyncSQLiteBM25Retriever.source_context` 用原KnowledgeStore.verify_evidence及read_adjacent_context，按片段ID、知识版本、文档ID/版本读取；不按标题猜同源、不执行MATCH后过滤、不读取整篇文档。冻结上限为12个原交付片段；邻接depth1、最多6片段/2400字符、允许跨页且保持storage_order；整池最多16000字符，且服从更严格的每次/总字符及期限预算。超限拒绝，不偷偷截断原引用；邻接省略明确保留。

初审同时产生已有literal单元状态和成立缺陷。证据不足/无法评估且没有成立缺陷的单元，按原文单元、既有组件稳定次序形成缺口，记录原主张、限定、对象ID、既有范围、查询及结果。只对document_body/technical_content补检；相同完整查询去重，每个审核版本最多3个不同查询、一次补检轮次。剩余项明确query_limit/no_eligible_component，不能预算耗尽自动通过。没有另加路由模型，也没有把全体主张拼大OR。

补检复用RetrievalSession；实际证据按对象映射，原引用仍只核验自身绑定。再次事实审核覆盖完整原文，先前成立缺陷和对应不利单元保留稳定finding_id，非成立单元判断可被新审核替代；领域首次发现保留。补检失败保留同级结果并进入执行失败。合法缺陷仍走原一次Revision；新版本重新提取、来源映射及完整双审，复用证据身份不复用支持判断。原生成快照不回填后来的补检。

预计节省来自替代首轮无条件事实/领域全库检索；新增成本是来源直接校验及不足项的有限补检和事实复审。改变了审核范围，不能称同等能力的纯算法A/B。初审错误支持仍可能漏过，来源本身错误也可能忠实通过。

## 预算准入停止，而非模型消费超额

任务上限每链12次、全批96次及输入输出合计1200000 token，输出额度沿用8000。离线构造真实候选首审载荷，包括完整原文、主张、quote候选、供给及逐组件绑定；不发送。采用明确保守的UTF-8内容字节＋2048信封余量＋最大输出预留，不假称是提供商精确tokenizer。

新增SendLimit用锁对请求数、链额度、全局token及期限进行持久化原子预留，发送前写账本，失败即停止；不事后扣费或回收不确定预留。该防护在离线并发测试中验证，**本轮没有接入真实批次运行**；完整可发送批次没有被预算准入。实际请求0、实际输入/输出token0；费用金额及账单币种未知，未查账单。完整[预检摘要](preflight.json)与私有wire/hash分开。
