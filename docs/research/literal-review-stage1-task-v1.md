## 4. 必须贯通的业务实现

### 4.1 原文为主要审核对象

复用services/answer_anchors.py及已有回答/引用位置。事实审核直接判断版本绑定回答单元的完整意思，提供完整回答上下文处理指代与条件。提取结果可继续承担检索/诊断，但不能以失真的提取命题替代原文判错，也不能因提取漏项而将该原文静默标为已审。提取失败的执行状态仍如实保留，不以使用原文自动掩盖失败。

每个需要审核的原文单元必须有明确记录；不能只返回错误列表并推断其他内容支持。同一单元可含正确与错误部分，必须定位具体缺陷。程序位置覆盖不等于语义完整，所有条件/量词/否定/因果/义务强度仍由模型审查。

独立支持、原引用支持、来源身份/可靠性、任务工程边界分别保留。邻接文本只能用于正确理解上下文，不是程序自动继承条件的依据；不得跨原引用范围借来源。新增发现可能需要复用检索结果的合法集合，必须保留原delivery约束和出处，不能扩大为整个库已支持。

优先用一份明确的业务结论及具体差异替代重复语义状态组合。不要预定字段数量或复制新一套复杂条件矩阵；也不能退化为一个pass布尔值。ID/版本/位置/逐字来源由程序绑定；不得用理由关键词或模糊匹配重判标签、补条件、清洗非法JSON或制造支持。

现有组件型数据结构若无法诚实表达原文审核，允许增加最小候选结果类型及显式兼容读取。不得伪造旧component supported/fidelity faithful来满足旧政策，不把所有旧组件一键标为通过。旧路径和历史读写继续可用。

### 4.2 有据发现与替换正文分责

事实审核输出实际问题位置、合法来源、原文与来源的差异，以及来源能够支持的纠正边界，不必预写最终替换答案。修订者负责写替换正文。

候选修订资格必须绑定当前回答版本、真实定位和确实交付的合法正文依据，并要求明确的可纠正差异。无支持内容不自动等于矛盾；单有相关主题、疑点或建议不足以取得修订资格。程序能验证出处和结构，不能声称机器已证明纠正语义。未知/缺输入/执行失败独立保留。

复用原确定性政策底线：执行完整性、危险边界、一次业务修订、剩余缺口不能靠删除题目消失。已存在至少一项有据发现即可修订的能力，不重建这一机制。确需变更的资格规则另版显式选择；不用空replacement或rationale内伪造旧标记绕门禁。

### 4.3 局部修订与不修改结果

Revision一次返回对程序给定原文单元的替换和逐发现处置；程序拼装新答案并原样保留未选单元。保留完整上下文供模型判断，不按字符相似度证明语义正确。

校验版本、目标存在、重复/冲突替换、引用更新和来源作用域；位置由程序重新计算，旧引用不能错误贴到新正文。未改正文/引用的保留须有可核验比较。修改段落内正确内容及任务必答信息另做语义评价。

允许一次同时修改前提和直接依赖结论，不建立新知识图谱，不把错误下游结论永久锁住。修订过程解释写动作记录，正文直接回答原题。不得默认把多段答案压成一两段，不删必答内容满足长度；用户显式限制仍遵守，生产默认长度不顺带修改。

允许明确的无修改结果：全部retained/unresolved时保留原版本，记录一次修订尝试、未解决争议并终止，不能因此pass或再次修订。预算/循环不能因版本未增加而重置。不得把合法无修改误报为JSON执行失败；亦不得把它计为改对。修改成功则沿现有流程重新提取、完整事实审核与领域审核。

### 4.4 范围控制

## 9. 评价和第一阶段结论

每题交付可回查对照：问题/依据 → 初稿 → 两路发现 → 处置/改动 → 最终正文 → 重审 → 独立文本复核。先看来源与正文，再看模型理由；可由只读审阅子Agent盲看版本文本，仍明确AI辅助而非额外真实模型裁判/专家标注。

必须分别统计改对、漏修、误改、正确内容删失、新增错误、必答点保留、合理未解决、错误认可、执行失败和成本。mixed结果单列，不用一个加权总分抵消关键损害。无变化的正确稿是保护成功，无变化的错误稿是漏修；重审pass不作为独立质量真值。全部计划槽、失败和未执行均保留，不只报完成子集。

以下是第一阶段预先约定的工程判断线，不是统计可靠性声明，也不是生产准入门槛：

1. 候选4份错误稿至少3份实质修复目标错误，且义务强度、条件归属两份必须修复；相关修改均完成完整双重审并能读取历史/引用。审核标签未过但独立复核认为正文改对时，分开报告“内容修复”和“系统交付未闭合”，不能算完整贯通。
2. 3份正确保护稿均保留正确含义和必答点，没有错误不利判定或无据改写；证据不足稿不被伪造成矛盾或强行补全。
3. 候选已完成结果中无新增关键错误、无必答信息删失；未改单元的程序保留验证成立。
4. 自然线无论好坏全部如实报告；没有可修机会或没有改动不能宣称自然收益。观察到内容改善但仍有交付阻断，照实说明。

能力线与保护项未达标：结论为本候选未形成所需能力，停止本阶段，不追加提示变体。
能力线达标而自然收益未证实：只建议保留开发候选，不自动下一批。
两线出现可复核收益且未伤害保护项：可建议下一阶段独立验收，但仍不生产采用、不自动启动后续实验。

不要为了达到3/4更改关键错误定义。模型自己声称modified/支持不是修复成功；成功案例的源、改动和仍存限制必须让项目所有者可以复核。

## 10. 收尾与交付

公开目录建议docs/evaluation/literal-review-stage1-v1/，私有运行目录沿既有data规范。公开短报告、必要预测原文、逐题前后答案及来源定位、配置/冻结身份、调用/失败/未执行统计和回退方式。源全文、实际完整输入/响应、数据库、模型、凭据留忽略data；不做ZIP或副本。

学习站只定向补一个“原文审核与局部修订”案例/源码导读，包含实际成功或失败、取舍及适量练习；不重建全站、不凑章题数。若候选失败，教学按失败写，不能预写收益。完成相关构建/链接核验，未做浏览器验收就明确未做。

更新handoff、documentation-index、design-decisions和必要手册素材；用户确认的范围、实现事实与模型效果分开。检查实际源码/冻结身份、数据未误暂存、资源已释放、生产未切换。普通提交、推送本任务分支并核对远端允许，无需再问；不强推或自动合并。公开推送必须只含本任务及确有必要的规划文档，不带未授权论文/原始数据/其他研究。

最终回复以“达成了什么、没达成什么”开头，给提交SHA和远端报告链接，展示至少一个完整前后案例（若无成功则展示最有解释力的失败），列实际调用/成本、测试结论、剩余限制及建议。不要只列测试数量，不用“下一步可以继续”替代本阶段收尾。做到此处停止，等待设计对话审阅。
